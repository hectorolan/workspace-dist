# CLAUDE.md — the CEO's workspace conventions

This file lives in the workspace repo, cloned at `sources\workspace`. Project repos are siblings, cloned directly under `sources\` (not children of the workspace repo). Repo-level CLAUDE.md files override it for repo-specific details.

**Sessions always start from `sources`** (the container directory). `sources\.claude` is a junction (Windows) / symlink (Linux) into `workspace\.claude` — one copy of the config, tracked in the workspace repo, loaded in every session. This lets the orchestrator see all project repos at once and delegate work that doesn't collide. Agents working inside a project repo must run git with `-C sources\<repo>` (or cd into it) and read that repo's own CLAUDE.md first.

## Who works here
Solo developer — the CEO. Claude does the implementation; the CEO reviews and merges. Human review is the merge and production-deploy gate — one carve-out only (the CEO, 2026-08-01): **Dependabot PRs on the workspace repo** — green patch/minor bumps auto-merge in CI (`ci.yml` `automerge`), and red ones are triaged, fixed, and squash-merged by the scheduled `jr_implementer_github_dependabot` path behind mechanical guards (the four guards and their enforcement: SYSTEM.md "Dependabot red-PR triage"). Majors, every other author, and every other repo keep the human gate.

## Agents
- `orchestrator` — dispatch + status + regression reporting. Entry point for "work through my backlog" or "status of everything".
- `implementer` — feature/bug work, follows the project-iteration skill.
- `jr_implementer_github_dependabot` — red Dependabot PRs on the workspace repo ONLY (the merge-gate carve-out above): diagnose, fix without touching tests, merge through the guarded tool. Dispatched by the scheduled `dependabot-triage` job, never for general work.
- `devops` — tests, CI, releases, staging deploys, and local Windows hosting (Task Scheduler jobs, see SYSTEM.md).
- `newsroom` — the daily digest ("personal newspaper"): world/tech news quick reads, a daily tech-learn section, and the unvetted idea-sparks section (its contract — count, labeling, no-evaluation rule — lives in the daily-digest skill §5, not here). The DB holds the full digest history (`message` kind `daily-digest`); the compose file lands in the per-machine data dir (`WS_DATA_DIR`, job-out) and the job runner (not the agent) delivers it by email. Finances content is informational only — never advice, never execution.
- `coo` — the business operator (the human = CEO, orchestrator = chief of staff, coo = business side): the on-demand market snapshot and the business-viability review of product definitions before the implementer builds (research, demand evidence, validation-before-building, go/no-go recommendations). Recommends; the CEO commits (spending/accounts/legal are always `blocked` → the CEO).

Before editing agent files, read `.claude/agents/README.md` (YAML gotchas + how to verify registration).

## GitHub sync (multi-environment prerequisite)
The workspace repo (github.com/hectorolan/workspace) is the source of truth shared by every environment that runs this setup. **The supported environments, what each one is for, and every change to them live in `.claude/environments/environments_setup.md`** — the one doc on the subject; its summary block is the quick read, and `configs/environments.json` is the machine-readable config it points at. Never restate the roster elsewhere. Rules for every agent, every environment, every session:
1. **Pull before work.** At session start (or before touching any workspace file), `git pull --rebase` in the workspace root. Never work on stale files. (Every environment also auto-pulls every 15 min — the container's `ws pull` job in `configs/jobs/jobs.json`, each PC's `Claude-WorkspacePull` task running `node cli\ws.js pull` directly (S4U, no wrappers) — so agents/skills/docs stay current between sessions; that safety net does not replace this rule.)
2. **Push after updates.** Any change to workspace files — docs, instructions, scripts — is committed and pushed **in the same session**, with ONE call, identical on every platform: `node workspace/cli/ws.js sync "<conventional commit message>"`. (Runtime/derived state — digests, reports, inbox captures, run logs, the offline fallback — lives in the per-machine data dir `WS_DATA_DIR`, outside git; it is never pushed. The DB is its source of truth.) A script owns the git lifecycle; the AI only produces content. Sessions that may overlap another session's work SHOULD pass `--paths <p1> <p2> ...` to commit only their own files (the f1804b1/d4c6366 lesson — default whole-tree sync sweeps concurrent sessions' in-progress files; it now prints what it commits, reports what `--paths` left uncommitted, and warns on multi-area commits), while scheduled runners keep the default whole-tree sync. Scheduled jobs are pushed by their runner — agents in those sessions run no git at all. Unpushed changes are invisible to every other environment: treat them like unlogged work (if it's not pushed, it didn't happen).
3. **Workspace repo syncs directly on `main`.** This repo holds docs, logs, reports, and automation scripts — no product code — so the branch+PR rule is carved out here for sync to work unattended (reaffirmed by Hector 2026-07-16: keep main-direct so every environment stays in sync). Project repos keep the full branch → PR → review flow, no exceptions — **and project-repo work is managed through the specialized agents**: the orchestrator dispatches and tracks it, the implementer writes the code and opens the PR, devops handles tests/CI/deploys. A main session shouldn't hand-edit a project repo directly; route it through them.
4. **The `ws log` offline fallback is `<WS_DATA_DIR>/fallback/log.md`** (the workspace's, unversioned; each project repo's `ops/log.md` is likewise a gitignored, local-only offline fallback — never committed, its audit history lives in the central DB). Lines land there only when the logging client can't reach the API, and `ws pull` replays them into the API on the next healthy tick (then archives the file) — so no line is lost or stranded, and the file never rides git. Never hand-edit it; `server/import-log-md.js` is the manual disaster-recovery re-import.
5. **Adding or removing an environment:** follow the procedure in `.claude/SETUP.md` ("New environment bootstrap" / "Retiring an environment"), then record the outcome in `.claude/environments/environments_setup.md`. SETUP.md owns *how you set it up and configure it*; the environments doc owns *what currently exists and in what state*.
6. **Project repos** live as siblings of `workspace/`, directly under `sources\<repo>`, as their own GitHub repos — outside the workspace repo's working tree entirely, so no `.gitignore` entries in the workspace repo are needed for them.

## Logging convention (the audit trail)
The audit trail is a **central SQLite table** (one DB on the live host), written through the log API in `workspace/server/` (see its README). Every agent operation is exactly ONE call — never a file edit, never a git command:

```
node workspace/cli/ws.js log -a <agent> [-r <repo>] <area> <status> "<message>"    # every platform
```

Statuses: `PR-open`, `done`, `blocked`, `failed`, `deployed-staging`.
Reading status: `node workspace/cli/ws.js query --summary --days 14` (portfolio sweep) or `--repo <r> --days 7`. **`ws` (node cli/ws.js) is the one client** — full subcommand roster documented in `cli/README.md` (one doc, never restated; `server/README.md` documents the API it speaks to); any new script must reuse it (or `cli/util/` modules), never reimplement API calls. Do **not** read fallback md files for status — the DB is the source of truth. If the API is unreachable, the client appends a classic md line to `<WS_DATA_DIR>/fallback/log.md` (sync rule 4), so no entry is ever lost; `ws pull` replays it when the API is healthy again.
Scheduled runs don't log at all — the job runner records the run itself. **Plans live in the central DB too** (source of truth since 2026-07-23): read/write only via `ws plan` (endpoints documented in `server/README.md`; rendered on the hub Documents page) — never as md files in the repo. Nine scripted log-writer exceptions, detailed in SYSTEM.md except where noted: inside `ws pull` — the PR watch (`pr-watch`, PR state transitions), the stale-status sweep (`status-sweep`, resolving a dangling non-terminal line whose cited PR/test-plan is provably finished), the fallback replay (`fallback-replay`, only when a queued line fails to replay while the API is reachable) and the tunnel watch (`tunnel-watch`, a confirmed ssh respawn, or a connect failure diagnosed as an NSG ssh-allowlist mismatch — cause and fix command); inside `ws sync` — the ci-guard (`ci-guard`, refusing a push that would land main red, or recording that warn mode / `--no-guard` let one through); spanning `ws sync` and `ws pull` — the plan close (`plan-close`, a test-plan closed or held against the last green run: after a green push, and on every pull tick judging the stored baseline); spanning `ws pull` and the scheduler — the self-restart (`self-restart`); inside the scheduler — the log-API supervisor (`api-watch`, a confirmed server replacement); and inside the log API itself — the page-comment lifecycle sweep (`comment-lifecycle`, a `waiting` comment expired or a stale claim reverted; detailed in `server/README.md` "Page-comment lifecycle"). If it's not in the log, it didn't happen.

## Living documents (self-updating md files)
CLAUDE.md, .claude/SETUP.md, SYSTEM.md (technical spec of what runs on this machine — scheduled tasks, components, data locations), every file in `.claude/agents/`, and every skill are living documents. Rules for every agent, every session:
1. **Read .claude/SETUP.md before assuming access** to GitHub, hosting, CI, or cron. If access is missing, follow the protocol in .claude/SETUP.md (walk the CEO through it, verify, mark ✅).
2. **When reality changes, update the doc in the same session**: a completed setup step → SETUP.md; a new convention or correction from the CEO ("always do X") → the relevant agent file or skill; a workspace-wide rule → this file. Then record the doc change with one `node cli/ws.js log` call.
3. **Repo docs ARE the shared memory** (Hector 2026-07-19): Claude's local memory directory is machine-private and invisible to every other environment. Any lesson, convention, or fact that another environment or agent could need goes into the repo doc where it applies — local memory keeps only machine-personal session context. If it matters and it's not pushed, it didn't happen.
4. **Tell the CEO what you changed** in one line ("Updated SETUP.md: gh auth ✅").
5. **Living docs show only current truth** (Hector, 2026-07-20): no legacy references, no "revisit on \<date\>" deferrals — a decision is either made now or waits on a concrete event. Retired features and completed/rejected plans become DB plans that KEEP their kind (`plan`, `audit`, `design`, `doc`, …) and get `status: archived` (via `ws plan set ... --status archived` — archived is a STATUS, never a kind: the CEO, 2026-08-02), reachable through `ws plan list --status archived` (or are deleted — git history keeps everything). READMEs, skills, and agent files describe only what is valid and how to behave NOW: stale mentions are noise that confuses both models and humans, so filter them out the moment something becomes legacy. And **each fact lives in ONE doc — others cross-reference it, never restate it** (Hector, 2026-07-20): duplicated facts are where drift starts, since every copy will eventually be true in one place and false in the other.
6. Tip for the CEO: in Claude Code, starting a message with `#` offers to save that instruction into CLAUDE.md automatically — the quick way to teach a permanent rule.
7. **DB-only vs file — the churn test** (Hector, 2026-07-24; design `ws plan get stale-md-elimination-design`): a document belongs in the **central DB** (via `ws plan` or the `daily-digest`/report message kinds) when its content is generated or regenerated on a cadence — digests, logs, reports, rolling summaries, run outputs, inbox traffic: churny artifacts that accrete and go stale as files. Runtime/derived byproducts go to the per-machine data-dir (`WS_DATA_DIR`, sync rule 2), never git. A document stays a **file in the repo** when it is hand-authored config/reference/spec read to operate or bootstrap the system — the living docs above plus code-coupled READMEs. **Frequent hand-edits do NOT make a doc DB-only**: churn means machine-generated cadence, not often-revised-by-an-agent (so SETUP.md/SYSTEM.md stay files despite heavy editing). Two hard overrides keep a doc a file regardless: the **harness** loads `.claude/CLAUDE.md`, agent files, and skills from disk at startup; and **bootstrap/offline** docs (how to obtain access; anything read while the API is down) must be readable without the DB. When a new feature would emit a cadence-generated `.md` into git, this rule routes it to the DB/data-dir at birth. **The invariant underneath** (Hector, 2026-07-24): a fresh clone of this repo with an EMPTY DB must already be a fully-functioning, fully-evolved agent system. Everything the system needs to *be itself* — config, agent files, skills, conventions, bootstrap/recovery docs — must travel in the repo; the DB holds only accreted per-instance history (logs, digests, reports, plans) that legitimately starts from nothing (a new operator hasn't lived it yet). That is the real line: **repo = the system's definition; DB = its memory.** If a doc's absence from a fresh clone would break or under-evolve the agents, it is a repo file; if its absence just means "no history yet," it is DB content.

## Standing rules
- **Agents dispatch one at a time** (Hector, 2026-07-25): sequential dispatch only — never run two agents concurrently against the repos. One agent finishes (reply received, its sync/PR settled) before the next launches. Why: concurrent pipelines caused the `f1804b1` sync sweep (one session's `ws sync` swept another's files), and parallel open PRs collide when the CEO reviews/merges. Read-only evidence gathering with no writes is exempt but still shouldn't overlap a writing agent on the same repo.
- **Every pending item lands in the backlog plan** (Hector, 2026-07-25): when a follow-up, deferral, or awaiting-the-CEO item surfaces anywhere — a conversation, a plan, an audit, a doc, an agent reply — add it to the DB `backlog` plan in the same session, marked `awaiting <CEO>` or `dispatchable`, with the exact ws command that retrieves its source detail (`ws plan get <slug>`, `ws query --message-id <id>`, `ws query` conversation lookup). An item that lives only where it was mentioned is lost; the backlog is the single iteration surface (SETUP.md points agents at it). **Evidence a cross-station surface will cite is DB content at birth** (the CEO, 2026-08-15): if a backlog item, plan, or digest will reference it, store it as a DB plan (`ws plan set <slug> --kind doc --status archived --file <f>`) the moment it is written — the per-machine data dir is only for byproducts nothing else references, since a data-dir path is unreadable from every other station (and instance evidence is the DB's memory, never repo or package content). **Marking an item finished has ONE shape** (2026-08-01): prefix the item with `RESOLVED YYYY-MM-DD` at the very start (or file it under a `## Resolved (YYYY-MM-DD)` heading) — one marker word, ISO date immediately after; never delete the line by hand. The monthly backlog prune (SYSTEM.md "Monthly backlog prune") archives prior-month resolved material into `backlog-history-YYYY-MM` (kind plan, status archived; `ws plan list --status archived`); legacy markers (CLOSED/SHIPPED/DECIDED + date) stay recognized on existing items, but anything ambiguously marked is never archived — it just sits there as noise, so mark cleanly.
- **Artifacts carry their provenance** (the CEO, 2026-08-15): a conversation that generates a durable artifact (plan, doc, design, audit) does not stay a floating Conversations item — the generating session attaches the conversation's origin message to the artifact's document thread as a role-`trigger` entry and archives the conversation, in the same session: `node cli/util-tools/thread-attach.js <doc-kind> <doc-ref> --conversation <id>` (one command, idempotent). The artifact's thread then opens with where it came from; the Conversations list holds only live correspondence (`conv-status <id> active` reverses an archive). This generalizes the pattern the inbox runner already follows for docs born from page comments.
- **Never hide misbehavior** (Hector, 2026-07-19): when automation detects that an agent broke its rules (sent an email it shouldn't have, logged or pushed in a scheduled run), log the violation loudly as a `failed` compliance line and keep the evidence. Runners may prevent user-facing damage (e.g. skip a duplicate send) but must record having done so — never silently dedupe, suppress, or auto-correct.
- **No AI attribution anywhere** (Hector, 2026-07-16): commits, PR bodies, code comments, docs — no Co-Authored-By trailers, no "Generated with Claude Code" footers, no AI mentions. Work is authored as the CEO only. Enforced via `attribution: {commit: "", pr: ""}` in `.claude/settings.json`; agents must also not add such mentions manually.
- **Subagent report contract** (token rule, Hector 2026-07-21): a subagent's final reply to its caller is ≤10 lines — outcome, artifact paths, log line written, blockers. Bulky material (diffs, test output, research, logs) goes to a repo file with the path in the reply; the caller reads files on demand, never receives dumps. Why: the reply lands in the caller's context and is re-sent on every later turn for the rest of the session.
- **Tools over turns — every agent** (Hector 2026-07-19, workspace-wide 2026-07-21): before doing mechanical, repeatable, or parameterizable work with agent turns, check the Forged tools inventory in `cli/README.md` for an existing tool and run it. Rule of two: about to do the same mechanical thing a second time by hand → stop and forge instead — a small Node script in `cli/util-tools/` importing the shared `cli/util/` modules (never reimplement API/git/email calls), one-line row added to that inventory (name · what it automates · tokens it replaces), verified once, then used. Tools read secrets only from env, never carry credentials or prompts to other AIs, and land on main via `node cli/ws.js sync`. If forging is out of scope mid-task, flag the pattern as a "forge candidate" in the reply.
- **New capabilities register in the feature catalog** (`configs/features.json` — the declared registry behind `GET /feature` and the hub Features subtab; contract: `server/README.md` "Feature registry"): a new scheduled job, tool, or check gets its registry entry in the same session — env-doctor's `feature-registry` check WARNs on drift (SYSTEM.md), so an unregistered capability reports itself.
- Branch always; never commit to main.
- Conventional commits.
- **Fetch before any branch operation** (the CEO, 2026-08-02 — after repeated manufactured conflicts): run `git fetch origin` (ALL refs, not just your branch) immediately before every rebase, merge, branch cut, or mergeability check, and rebase onto `origin/main` — never a local `main`, which may be days stale. A rebase onto a stale base rewrites the branch BACKWARDS and manufactures conflicts that did not exist. Corollary (2026-08-15, after two stale-tree briefs in two days): **fetch updates refs, not files** — evidence about current code comes from `origin/main` (`git show origin/main:<path>` or a pull), never from an unpulled working tree; `node cli/util-tools/repo-freshness.js` is the one-command preflight that reports each repo's branch/dirty/drift verdict. Corollary: **any two open PRs on one repo WILL conflict in CHANGELOG.md** — every PR appends there, so never claim "no overlap"; the last-merged PR pays a changelog rebase (keep both entries), plan for it.
- **PR screenshots on private repos: link, never embed** (2026-08-01, hit live on ho-nexus PR #30): `![](...)` image embeds in a PR BODY cannot render from a private repo — neither branch-relative paths nor `?raw=true` URLs resolve for the browser. Commit the PNGs on the branch and put **plain links to their blob pages** in the body (they open GitHub's viewer with the reviewer's auth; the Files-changed tab renders them too).
- Implementer is two-phase: requirements (ask before coding if blocked) → test plan (written to the central DB via `ws plan set --kind test-plan --repo <repo>`, not a `docs/test-plans/` file) → implementation. Tests are part of the definition of done; devops audits test plans into regression baselines. **Test-plans close by script, never by agents** — two triggers, both in SYSTEM.md: a PR-repo plan closes when its PR merges (pr-watch), a main-direct-repo plan closes when a green run covers all of its automated case IDs (plan-close — after `ws sync`'s green push, and on every `ws pull` tick against the stored baseline). Either way, a plan held by unperformed manual cases stays active and gets a **CEO block** pinned at its top.
- **Tag plan-scoped tests at authoring time** (Hector, 2026-07-31): a test written purely to prove ONE test-plan's change does not live in the suite forever — the writer tags it in a `//` comment directly above its top-level `test(`: `@plan:<slug>` plus `@throwaway` (one-time proof, deleted when the plan closes) or `@promote` (guards behaviour that could regress — kept and untagged on close, graduating into the permanent suite). The judgement happens at writing time, while context is freshest; closure and cleanup stay fully scripted — the tag carries the decision, the reaper in `ws sync` executes it (mechanics, tag grammar edge rules, and the baseline strip: SYSTEM.md "Plan-scoped temp-tests"). An untagged test is permanent from birth.
- **The CEO is config, never a hardcoded name** (Hector, 2026-08-01): who the system works for lives in `ceo` in `configs/environments.json`, read only through `cli/util/ceo.js`. No source file names a person — change the config and the whole system addresses someone else, which is what makes CLAUDE.md's own "fresh clone is a working system" invariant true for a *different* operator. The CEO's **email is not there**: `OWNER_EMAIL`/`AGENT_EMAIL` own that fact in env and the mail path reads them directly — nothing in the mail path needs a name, nothing in the CEO-block path needs an address, so neither restates the other. In prose, write **"the CEO"** for anything instructional; keep a person's name only in a dated attribution, which is provenance and stays true forever.
- **The CEO block is only what is blocked on the CEO** (Hector, 2026-07-31): the blockquote pinned at the top of a held test-plan lists nothing but the things the CEO personally must do — never a summary of the plan, never what is already done. It is written and removed by `plan-close` alone, so it cannot go stale. Authors supply the colloquial one-liner per case under a `## Needs <CEO>` heading (`- TP-x-013 — <plain sentence>`); with no bullet the script falls back to the case description, which reads badly on purpose so a missing sentence is visible.
- **A manual test case is a last resort** (Hector, 2026-07-31): every manual case is a permanent tax on the CEO's attention, so before writing one, check that no machine could do it. hub already has a full browser suite (Playwright, `npm run test:e2e`, stub log-API, servers managed by the config) — anything about what a page renders belongs there, not in a manual case. Reserve manual for what genuinely needs the CEO's hands or decision: live-VM checks, credentials, accounts, go/no-go calls.
- Secrets only via env vars; keep `.env.example` current.
- **All script dates/hours/log stamps come from `cli/util/clock.js`** (schedule timezone from `configs/jobs/jobs.json`) — never `new Date().toISOString()` for calendar dates. UTC dates ran the 2026-07-20 digest a day early (evening catch-up composed "tomorrow's" digest); raw instants (`Date.now()`, full ISO timestamps as IDs) are fine.
- **Plan rows are never deleted** (the CEO, 2026-08-02: "we don't delete, we just archive, and update"): the plan store is append/update/archive only — retiring anything means `status: archived` with its real kind kept. The `DELETE /plan` endpoint an implementer once added without authorization was reverted the same day; adding a destructive capability to the shared store is a CEO-class action, like merging and deploying — never agent initiative.
- **One decision at a time to the CEO — a stepper, never a wall** (the CEO, 2026-08-15, a repeated correction): when the CEO's input is needed, present ONE item with a recommendation, wait for the answer, record it, then the next. Batched decision dumps get batched answers back, which loses fidelity both ways. Status reports on request may be long; decision-asks never are.
- When blocked, log it and stop — don't guess on auth, payments, or migrations.

## Model routing
- The per-agent roster lives in each agent file's `model:` frontmatter, summarized in the doctor-guarded table in `.claude/README.md` — never restated here. The assignment principle (Hector 2026-07-26): the heavyweight model only where the work is long autonomous coding or business judgment that gates what gets built; dispatch/status/deploy-diagnosis run on opus at lower cost; high-volume compose and mechanical-triage agents run on sonnet.
- Scheduled headless runs: the provider seam (`cli/util/agent.js`) launches the outer dispatcher session on **haiku** (`AGENT_MODEL` env var to override); the subagent's own `model:` does the real work.
- Fallback: configure the session fallback chain so flagged, unavailable, or rate-limited Fable requests continue on Opus (see "Fallback model chains" and "Automatic model fallback" at https://code.claude.com/docs/en/model-config). A model switch never changes the workflow rules above.
